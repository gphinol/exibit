Feature Description

Fortan Pro already computes the whole decision apparatus inside the ROI Lab: a FR-002 verdict decision matrix (Strong Buy / Buy / Hold/Consider / Neutral / Avoid), a Monte-Carlo distribution with P10/P50/P90, VaR/CVaR, probability of profit, comp-backed sample sizes, index publication status, FX provenance, per-parameter resolution levels (data_levels), freshness, engine version, and blocking reasons. All of it exists — but it is buried across four report tabs and a PDF that still leads with an Executive Summary.

This feature adds a first-class Decision Layer capability to the existing underwriting workflow:

  • One canonical decision_layer object on AnalysisResponse, computed once in the backend from the exact analysis snapshot that ships in that response.
  • A Decision Card rendered as the first interpretation layer above the detailed analytics (top of the Summary tab).
  • A restructured report hierarchy (Prompt §11) applied to every report surface: the sealed institutional PDF, the Jinja report templates (roi_print, institutional_memo, market_overview), the client print export, the quick summary, and the Excel working copy — decision first, then snapshot, return profile, scenario/uncertainty, valuation/market, evidence quality, risk/assumptions, decision logic, verification.
  • The institutional_memo template is upgraded from a concise memo into a detailed Committee Packet modeled on published pension committee packets (WSIB Private Markets agenda + manager/consultant decks; SCERS action items; CalPERS committee memo): Agenda with Action/Information items → Executive Summary & Recommendation → Investment Strategy → Asset Profile & Terms → Market Analysis & Benchmarks → Underwriting & Return Profile → Scenario & Sensitivity → Comparable Evidence & Valuation → Due Diligence & Evidence Quality → Risk Assessment & Mitigants → Decision Logic & Conditions → Verification & Provenance → Appendices (assumptions, data resolution, important information). The sealed PDF plan is unchanged by this upgrade.
  • Production-safe verification URLs with a Mission Control admin setting (PDF_VERIFY_URL_TEMPLATE) so localhost can never reach a sealed document, plus admin-editable allowed domains.

No new financial logic, no new thresholds, no fabricated confidence. Every value is a passthrough, a re-label, or a comparison against thresholds/config that already exist in the engine.

User Story

As an investor, analyst, or adviser running a Fortan underwriting
I want the decision, the drivers, the evidence quality, and what would change the call — first in the UI and first in every report I export, with a production verification URL on sealed documents
So that I can move from “here is an ROI number” to “here is what the evidence implies about this decision” without searching through a 15-page memorandum, and so any recipient can verify the document against a real domain.

Problem Statement

The intelligence is buried. A user running the ROI Lab sees a verdict string inside an executive summary, blocking reasons inside a quiet note, evidence status inside the Market tab, and provenance inside the Institutional tab. Nothing answers, in one place and in order: What is the decision? Why? How strong is the evidence? What is uncertain? What would change it? The same is true of every exported artifact: the sealed PDF, the Jinja templates, and the client print export all lead with summaries rather than the decision. Additionally, POST /api/roi/pdf passes str(request.base_url) as the QR verify base — in any non-production deployment a sealed document can carry a http://localhost:8000/... verification URL, and there is no admin surface to set the production verify URL.

Solution Statement

Add an additive decision_layer block to the existing AnalysisResponse, generated by a new DecisionService (backend/services/roi/decision.py) that consumes only the already-formatted response plus the existing roi_result. The decision status is a deterministic relabel of the existing verdict + blocking reasons (mapping table below) — the engine verdict strings stay untouched. Drivers, evidence-quality items, conditions and unknowns are selected from fields that already exist. Every report surface is then restructured to the Prompt §11 section hierarchy and reads from that same object. A new admin config surface (GET/POST /api/admin/verify-config + a Mission Control settings card) manages PDF_VERIFY_URL_TEMPLATE and PDF_VERIFY_ALLOWED_DOMAINS, and the sealed PDF refuses to emit a localhost verification URL in production.

Phase 1: Backend contract + DecisionService

Create the additive response contract and the deterministic generator. The generator consumes the already-built AnalysisResponse (canonical snapshot) plus roi_result (for _base_verdict_from_roi) — it performs no calculations of its own.

Status mapping (locked by this plan, derived from the existing matrix):

Base verdict (_base_verdict_from_roi) Final verdict (_apply_verdict_decision_matrix) status status_label
Strong Buy / Buy same as base, no blockers proceed PROCEED
Strong Buy Buy (probability-only blocker) proceed_with_conditions PROCEED WITH CONDITIONS
Buy Buy, probability-only blocker held proceed_with_conditions PROCEED WITH CONDITIONS
Strong Buy / Buy Neutral (data-availability blockers held) insufficient_evidence INSUFFICIENT EVIDENCE
Hold/Consider Hold/Consider monitor MONITOR
Neutral Neutral (band verdict, no downgrade) monitor MONITOR
Avoid Avoid avoid_for_now AVOID — FOR NOW

Driver selection (fixed priority, cap 6, include only when the value exists):

priority key category source path on AnalysisResponse
1 real_return RETURN financial_analysis.detailed_roi_analysis.expected_real_roi
2 downside_p10 DOWNSIDE financial_analysis.investment_scenarios[scenario=="pessimistic"].roi (fallback: detailed_roi_analysis.var_95)
3 evidence_sample EVIDENCE market_analysis.property_market.index_sample_size else properties_available (guarded by index_sample_size/properties_available_available)
4 market_index MARKET market_analysis.appreciation_provenance.status (fallback market_analysis.price_index_*)
5 title_risk TITLE detailed_roi_analysis.title_risk_factor (only when title_type supplied and not unknown)
6 confidence MODEL executive_summary.confidence_level
7 probability_profit RETURN detailed_roi_analysis.probability_gauges.positive_return (fallback risk_analysis.probability_positive_return)
8 liquidity LIQUIDITY detailed_roi_analysis.exit_liquidity_score

valuation (subject vs comp median) is merged by the frontend from the existing backend GET /api/roi/comparables?price=… response (ComparablesValuation.price_vs_median_ratio) — backend-computed, no local math. The sealed PDF’s Decision section additionally picks it up from report.market.valuation when the payload carries it.

Evidence Quality (cap 6): index publication status, comparable sample n, data freshness, FX basis, local coverage (proxy detection from data_levels[*].is_proxy), missing inputs (missing_data_fields), price basis (listing-derived, grounded in docs/price-index-methodology.md, only when the index source was used).

Conditions (“What would change this decision”): derived only from held blockers + configured bands:

  • return threshold: real ROI vs _risk_tolerance_bands(params.risk_tolerance)['hold_threshold'] (AVOID/INSUFFICIENT EVIDENCE) or ['buy_threshold'] (MONITOR); basis states the band.
  • "comps thin (n < 3)" / "properties_available == 0" → comparable sample reaches _VERDICT_COMPS_QUORUM.
  • "probability_positive_return < 0.6" → probability reaches the 0.6 threshold.
  • "economic data stale" → freshness gate clears.
  • "title missing or unverified" → verified title supplied.
  • "infrastructure_score unavailable" / "security_score unavailable" → local evidence becomes available.
  • "demand_trend == Low" → listing count reaches the Low band boundary (20, per VerdictService._derive_demand_trend).
  • Empty → reentry_note = "No deterministic re-entry trigger available for this analysis." (exact Prompt string).
